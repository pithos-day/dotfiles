# テスト可読性チェックリスト

> **基本定理**: テストコードの可読性も本番コードと同じくらい重要。他の開発者はテストを「正しい使い方の非公式ドキュメント」として読む。テストが読みやすいと追加・変更もしやすくなる。

## 1. テストの本質を1行に凝縮する

- テストの本質は「この入力・状況に対して、この出力・挙動を期待する」。多くは1行で表現できる。
- ヘルパーで重要でない詳細を隠す:
  - `MakeScoredDoc()` → `AddScoredDoc(docs, score)` → 最終的に `CheckScoresBeforeAfter("1, 2, -1, 3", "3, 2, 1");`
- カスタム「ミニ言語」(文字列で入出力を表現するヘルパー)は強力。テストの追加がコピペ地獄にならない。

## 2. エラーメッセージを読めるようにする

- 素の `assert(a == b)` は「何が違ったのか」が出ない。高機能なアサートを使う:
  - C++: `BOOST_REQUIRE_EQUAL(output, expected_output)` → `["1, 3, 4" != "4, 3, 1"]`
  - Python: `self.assertEqual(a, b)` → `AssertionError: 1 != 2`
- 必要なら手作りアサートで、バグを追跡しやすいメッセージを出す:
  ```
  CheckScoresBeforeAfter() failed,
    Input:           "-5, 1, 4, -99998.7, 3"
    Expected Output: "4, 3, 1"
    Actual Output:   "1, 3, 4"
  ```

## 3. 良いテスト入力を選ぶ

> **コードを完全に実行する、最もシンプルな入力セットを選ぶ。**

- 意味のない「派手な」値は避ける: `-99998.7` → `-1`(ただの負数なら)。「とても負」なら `-1e100` のような明確な値。
- シンプルすぎて機能をテストしない値もダメ: `"1, 2, 3"` は負値フィルタを試せない。
- **1つの完璧な入力で全部を試すより、機能ごとに複数の小さなテスト**を書く:
  ```
  CheckScoresBeforeAfter("2, 1, 3", "3, 2, 1");    // Basic sorting
  CheckScoresBeforeAfter("0, -0.1, -10", "0");     // All values < 0 removed
  CheckScoresBeforeAfter("1, -2, 1, -2", "1, 1");  // Duplicates not a problem
  CheckScoresBeforeAfter("", "");                  // Empty input OK
  ```
- 失敗したテストはどこが悪いかを特定しやすい(テストが分かれていると)。
- 大きな入力を手で書くのではなく、プログラムで構築する(10万要素など)。

## 4. テスト関数の命名

- `Test1()`, `Test2()` は無意味。`Test_<FunctionName>()` または `Test_<FunctionName>_<Situation>()` を使う:
  - `Test_SortAndFilterDocs_BasicSorting()`
  - `Test_SortAndFilterDocs_NegativeValues()`
- テスト関数はコードベース中で呼ばれないので長くて構わない。名前はコメントとして機能し、失敗時の出力にも出る。
- フレームワークの慣習(Python unittest の `test` プレフィックス等)があれば従う。
- アサートを含むヘルパーは `Check...()` のように名前で区別する。

## 5. テストしやすい設計が良い設計

- テストが書きにくいコードは設計が悪いサイン:

| 特性 | テストしにくさ | 設計の問題 |
| --- | --- | --- |
| グローバル変数 | テスト毎にリセットが必要 | 副作用の影響範囲が不明 |
| 外部コンポーネントへの依存 | 準備が多くテストが億劫に | 失敗点が増え、リファクタリングしにくい |
| 非決定性 | テストがflaky | バグの再現が困難 |

- テストを書くことを前提に設計すると、自然と良い設計になる: 内部状態が少ないクラス、1つのことだけをする関数、疎結合、単純で明確なインターフェース。
- 「テストを書くのが悪夢だ」と感じたら、設計を見直す理由にする。

## 6. やり過ぎに注意

- 本番コードをテストのために汚さない(テスト用の配管を本番に埋め込むのは間違い)。
- 100% カバレッジへの執着は無駄になりがち(最後の10%は UI や低価値のエラーケース)。コストと利益の釣り合いで決める。
- テストがプロジェクトを支配してはいけない。

## 「8つの問題テスト」から学ぶ指摘ポイント

`Test1()` 例には最低8つの問題がある:
1. 長く、重要でない詳細で満ちている(1文で説明できるべき)
2. 新しいテストの追加が簡単でない(コピペの誘惑)
3. 失敗メッセージが役に立たない
4. 一度に全部をテストしている(機能ごとに分割すべき)
5. 入力がシンプルでない(`-99998.7` のような派手な値)
6. 入力を十分に網羅していない(0, 空, 重複, 巨大)
7. 極端な入力(空ベクタ、巨大ベクタ、重複スコア)を試していない
8. 名前が無意味(`Test1()`)

## 診断時のチェック項目 (要約)

- [ ] テストの本質が1行で表現できる形になっているか
- [ ] 失敗時に何が違ったのか分かるエラーメッセージが出るか
- [ ] 入力値がシンプルで、かつ機能を完全に試しているか
- [ ] 機能ごとに複数の小さなテストに分かれているか
- [ ] テスト関数名が `Test_<Function>_<Situation>` 形式か
- [ ] テスト対象のコードがテストしやすい設計か
- [ ] テスト追加が容易か(コピペせずに1行で追加できるか)
