# Refactor — コードリファクタリング

## Overview

既存コードの**理解にかかる時間を最小化**するためのスキル。「可読性の基本定理」を大原則とする:

> **コードは、他人が最短時間で理解できるように書かれているべきである。**

このスキルは「診断」と「修正」の両方に対応する。診断のみの依頼(レビュー型)と、修正まで行う依頼(ワークフロー型)があるため、作業開始時に確認する。

## When to Activate

- 既存コードのリファクタリング・可読性改善の依頼を受けたとき
- 「読みにくい」「何をしているか分からない」コードを指摘・修正するとき
- コードレビューで可読性の問題を指摘するとき

## 原則 (最優先)

1. **リファクタリングは振る舞いを変えない。** 挙動が変わる変更は「バグ修正」として扱い、別扱いにする。
2. **小さく、独立した変更を1つずつ**適用し、都度検証する。
3. **一貫性は「正しさ」より重要**。既存のプロジェクト規約・命名規約・lint 設定が本スキルの原則と衝突した場合は、プロジェクト規約を優先する。
4. 行数を減らすことより、**理解する時間を減らす**ことを目的にする。行数が減っても読みにくくなるなら逆効果。
5. コードがすでに読みやすいなら、無理に触らない。「完璧にファクタリングされたコードへの強迫観念」を持たない。

## Workflow

### Step 1: 対象の把握

- 対象コード・言語・プロジェクト規約・テストの有無を確認する。
- テスト実行コマンドを確認する(README / package.json / CI 設定など)。
- 依頼の種類(診断のみ / 修正まで)と範囲を確認する。
- リファクタリングのゴールを確認する(読みやすさ向上のみか、他に意図があるか)。

### Step 2: 診断 — チェックリスト走査

`references/` のチェックリストを以下の順で走査し、問題箇所を**ファイル:行番号 + 問題 + 該当原則**の形で列挙する。表面的な改善(低リスク・全コードに影響)から始め、構造的な変更(高リスク)は後回しにする。対象が大きい場合は依頼範囲・関数/ファイル単位で走査し、全量走査は避ける。

1. **名前** — `references/naming-checklist.md`
2. **見た目** — `references/aesthetics-checklist.md`
3. **コメント** — `references/comments-checklist.md`
4. **制御フロー** — `references/control-flow-checklist.md`
5. **式と変数** — `references/variables-expressions-checklist.md`
6. **構造** — `references/structure-checklist.md`
7. **テスト** — `references/test-checklist.md`

問題には優先度を付ける: 名前・見た目・コメントは低リスクで高影響。構造の変更はリスクが高いので、テストの有無を確認してから。

### Step 3: 適用

- 修正する場合は、チェックリストの1項目につき1変更ずつ、**Before/After 形式**で示しながら適用する。
- 各変更は振る舞いを変えないこと。変更に迷ったらユーザーに確認する。
- 例が必要な場合は `references/before-after-examples.md` を参照する。

### Step 4: 検証

- テスト・ビルド・lint を実行し、振る舞いが変わっていないことを確認する。
- テストが存在しない場合、それを報告し、構造的変更(制御フロー・変数・抽出)を行う前にユーザーの了承を取る。

### Step 5: 報告

- 変更点を「どの原則に基づくか」と紐づけて簡潔に報告する。
- 診断のみの依頼なら、指摘 + 修正提案(可能なら Before/After)を優先度付きで提示し、修正はユーザーの指示を待つ。

## 簡易チェックリスト (SKILL.md 内の要約版)

詳細は各 references を参照。**内容を変更するときは、対応する references も同時に更新すること。**

- **名前**: 具体的な単語を使う。tmp/retval 等の汎用名を避ける。単位・重要属性を付与する。範囲はスコープの大きさに合わせる。誤解されない名前にする(min/max、first/last、begin/end、is/has)。
- **見た目**: 類似コードは類似の見た目に。列揃え。意味のある順序。段落化。
- **コメント**: 自明なことを書かない。悪い名前をコメントで補わない(名前を直す)。理由・意図・定数の由来を記録。読者の「Huh?」を予想。簡潔に、曖昧な代名詞を避ける。
- **制御フロー**: 比較は変化する値を左に。if/else は正・簡単・面白いケースを先に。三項演算子・do/while・goto は回避。early return とガード節でネストを減らす。
- **式と変数**: 説明変数・要約変数で巨大式を分解(if 条件は2値まで)。ド・モルガンの法則。不要変数・中間結果・制御フロー変数を排除。スコープを最小化。write-once を好む。
- **構造**: 無関係なサブ問題を抽出。一度に1タスク。平易な言葉で説明してからコード化。コードを減らす(不要機能・未使用コード・標準ライブラリ活用)。
- **テスト**: 1テスト1行の本質へ。読みやすいエラーメッセージ。シンプルな入力値。Test_<Function>_<Situation> 命名。

## Gotchas

- **リファクタリング = 振る舞い不変**。挙動が変わる変更はユーザーに明示し、別の変更として扱う。
- **コメント削除は「コードからすぐ導けるもの」に限る**。理由・意図を書いたコメントは削らない。
- **悪い名前をコメントで補わない**。crutch comment を見つけたら、名前を直すことを優先する。
- **既存規約・lint が最優先**。本スキルの提案と矛盾しても、プロジェクトの一貫性を保つ。
- **言語固有の慣用句を尊重する**。本スキルの例は主に C系/Python/JavaScript だが、言語の標準ライブラリの慣習(イテレータ、range 表現など)は壊さない。
- **関数分割にはコストがある**。抽出しすぎると読みにくくなる。無関係なサブ問題の抽出を意図的に、ただし段階的に。
- **テストがなければ構造変更をしない**。まず動作の確認手段をユーザーに問う。
- **「もっと簡単な方法があるはず」という感覚を尊重する**。ロジックが複雑化したら、同じ問題を反対から解く・要件を疑うことを試す。
- **改名は呼び出し元に波及する**。変数・関数のリネーム時は grep で全参照箇所を確認し、漏れなく更新する。公開 API の改名は破壊的変更になるため、単独リクエストでは行わずユーザーに確認する。
- **変更中に挙動が変わったと気づいたら、その場で止める**。変更をリバートし、ユーザーに報告してから対処方針を確認する。
- **説明変数の追加と変数削除は一見矛盾する**。説明変数は「式の分解」「説明」「重複の圧縮」の少なくとも1つを果たす場合のみ残し、それ以外は消す。両チェックリストを順に走査しても同じ変数を残すか消すかで迷わないこと。
- **コメントの言語**は既存コードに従う(日本語なら日本語、英語なら英語)。
- 診断結果は「指摘だけ」に留めるか「修正まで」行うかは依頼次第。勝手に修正しない。

## Output Style

- 指摘は `ファイル:行番号` 形式で。修正提案は必ず Before/After コードで示す。
- 最終報告は「変更箇所 → 適用した原則 → 検証結果」の3点に絞る。
- 修正が複数にわたる場合は、1件ずつ順に示し、各修正後に検証してから次へ進む。
