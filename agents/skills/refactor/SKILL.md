# Refactor — コードリファクタリング

## Overview

既存コードの**理解にかかる時間を最小化**するためのスキル。「可読性の基本定理」を大原則とする:

> **コードは、他人が最短時間で理解できるように書かれているべきである。**

## 原則 (最優先)

1. **リファクタリングは振る舞いを変えない。** 挙動が変わる変更は「バグ修正」として扱い、ユーザーに明示して別の変更にする。
2. **小さく、独立した変更**を適用し、リスクに応じた単位で検証する。
3. **一貫性は「正しさ」より重要**。既存のプロジェクト規約・命名規約・lint 設定が本スキルの原則と衝突した場合は、プロジェクト規約を優先する。
4. 行数を減らすことより、**理解する時間を減らす**ことを目的にする。行数が減っても読みにくくなるなら逆効果。
5. コードがすでに読みやすいなら、無理に触らない。「完璧にファクタリングされたコードへの強迫観念」を持たない。

## Workflow

### Step 1: 対象の把握

- 対象コード・言語・プロジェクト規約を確認する。
- テストの有無と実行コマンドを確認する(README / package.json / CI 設定など)。テストがない場合は、構造的変更の前に動作の確認手段をユーザーに問い、了承を得てから進める。
- `git status --short` で作業ツリーの状態を確認し、作業前から変更があるファイルを控える。
- 依頼の種類(診断のみ / 修正まで)と範囲を依頼文から判断し、不明な場合だけ確認する。診断のみなら修正しない。

**構造的変更**とは、制御フロー・式と変数・構造の各チェックリストに該当する変更を指す。

### Step 2: 診断 — チェックリスト走査

問題箇所を**ファイル:行番号 + 問題 + 該当原則**の形で列挙する。対象が大きい場合は依頼範囲・関数/ファイル単位で走査し、全量走査は避ける。

読むチェックリストは依頼に合わせて絞る:

- **観点が特定されている依頼**(例: 「名前が分かりにくい」「ネストが深い」): 末尾の References から対応するファイルだけを読む。
- **全体的な診断**: 次の順で、各ファイル末尾の「診断時のチェック項目」を先に確認し、該当した項目の詳細だけを読む。低リスクな観点から順に進める。

1. 名前 → 2. 見た目 → 3. コメント → 4. 制御フロー → 5. 式と変数 → 6. 構造 → 7. テスト

指摘には優先度を付ける:

| 優先度 | 基準 |
| --- | --- |
| High | 誤読やバグを招く (誤解される名前、単位の欠落、追跡できない制御フロー) |
| Medium | 誤読の可能性は低いが、理解に時間がかかる (巨大な式、複数タスクの混在) |
| Low | 改善すると読みやすいが、影響は小さい (自明なコメント、順序の不統一) |

### Step 3: 適用

- 修正は **Before/After 形式**で示しながら適用する。
- 名前・見た目・コメントの変更はまとめて適用してよい。構造的変更は 1 件ずつ適用する。
- 各変更は振る舞いを変えないこと。変更に迷ったらユーザーに確認する。
- 例が必要な場合は `references/before-after-examples.md` を参照する。

### Step 4: 検証

- テスト・ビルド・lint を実行し、振る舞いが変わっていないことを確認する。構造的変更は 1 件ごと、それ以外は区切りのよい単位で実行する。

### Step 5: 報告

`assets/report-template.md` の書式で報告する。

- 指摘は `ファイル:行番号` 形式で示す。
- 修正した場合は「変更箇所 → 適用した原則 → 検証結果」の 3 点に絞る。
- 診断のみの場合は、指摘と修正提案を優先度順に示し、修正はユーザーの指示を待つ。

## Gotchas

- **コメント削除は「コードからすぐ導けるもの」に限る**。理由・意図を書いたコメントは削らない。
- **言語固有の慣用句を尊重する**。本スキルの例は主に C系/Python/JavaScript だが、言語の標準ライブラリの慣習(イテレータ、range 表現など)は壊さない。
- **フォーマッターが管理する書式は指摘しない**。Prettier / Black / gofmt などの導入済みプロジェクトでは、列揃えや改行位置の提案が整形結果と衝突する。
- **関数分割にはコストがある**。抽出しすぎると読みにくくなる。無関係なサブ問題の抽出を意図的に、ただし段階的に。
- **「もっと簡単な方法があるはず」という感覚を尊重する**。ロジックが複雑化したら、同じ問題を反対から解く・要件を疑うことを試す。要件の変更は提案に留める。
- **改名は呼び出し元に波及する**。変数・関数のリネーム時は grep で全参照箇所を確認し、漏れなく更新する。公開 API の改名は破壊的変更になるため、単独リクエストでは行わずユーザーに確認する。
- **変更中に挙動が変わったと気づいたら、その場で止める**。自分の変更だけをリバートし、ユーザーに報告してから対処方針を確認する。作業前から変更があるファイルには `git restore` などを使わず、自分の編集だけを手で戻す。
- **説明変数の追加と変数削除は一見矛盾する**。説明変数は「式の分解」「説明」「重複の圧縮」の少なくとも1つを果たす場合のみ残し、それ以外は消す。両チェックリストを順に走査しても同じ変数を残すか消すかで迷わないこと。
- **例集には挙動が変わる例がある**。見出しに「バグ修正を伴う」とある例は、リファクタリングとして適用しない。
- **コメントの言語**は既存コードに従う(日本語なら日本語、英語なら英語)。
