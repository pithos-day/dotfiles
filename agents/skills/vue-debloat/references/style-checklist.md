# <style> 肥大化チェックリスト

> **基本定理**: スタイルは「色・タイポグラフィ・スペーシング・共通コンポーネント」の 4 系統が
> 一元管理され、コンポーネント固有の装飾だけが scoped に残る状態が理想。

パスとコマンドの `src` は例。プロジェクトの既存の配置に合わせて置き換える。

## 検出観点 (4 種)

### S1. デザイントークンへ移すべき (値の重複)
- 頻出値がハードコードされている (font-size / gap / padding など):
  - 分布の確認: `rg -oNI "font-size:\s*[0-9.]+(px|rem|em)\b" src --glob "*.vue" | sed -E 's/:\s*/: /' | sort | uniq -c | sort -rn`
  - **10 箇所以上**: トークン化候補
  - **3〜9 箇所**: 同じ役割の値だと判断できる場合だけ候補
  - **1〜2 箇所**: 対象外
- 推奨先: グローバル CSS (例: `src/styles/global.css`) の `:root` に CSS 変数 (`--text-*`, `--space-*`) を定義して置換

### S2. グローバル CSS / 共通クラスへ移すべき (ルールセットの重複)
- **完全同一のルールセット**が 3 コンポーネント以上で重複している → グローバル CSS の共通クラスへ
  - 例: `.grow { flex: 1; min-width: 0; }` が 4 ファイル
  - 検出例: `rg -l "\.grow\b" src --glob "*.vue"` (クラス名ごとに定義ファイル数を数え、3 以上なら候補)
  - 移す前に、同名クラスの全使用箇所を確認する (グローバル化すると他のコンポーネントにも適用される)
- **グローバル CSS に既存のクラス (.row, .btn, .grow 等) が scoped で再定義されていないか**:
  - 完全同一なら、詳細度の変化を確認したうえで scoped 定義を削除して global を使用
  - 固有ルールのみ残す (例: `.row input` は残し `.row` 本体は global に)

### S3. 子コンポーネントへ分割すべき
- 1 つの style ブロックが **300 行超**、またはレイアウト・テーマ・状態ごとに責務が混在
- ロジック (script) を分割したコンポーネントと一貫させる (style だけ取り残さない)

### S4. パフォーマンス・保守上の問題 (指摘のみ)
- セレクタが過度に深い (5 段階以上のネスト、Sass 不使用でも CSS で深い子孫セレクタ)
- 巨大なメディアクエリの重複
- `!important` の多用 (10 回以上):
  - `rg -c "!important" src --glob "*.vue"`
- 修正すると詳細度が変わるため、依頼があり見た目を確認できる場合だけ修正する

## 除外ルール

- コンポーネント固有の 1 回きりの装飾 (100 行未満で可読性に問題がないもの)
- ライブラリ由来のスタイルの上書き (1-2 箇所程度)
- `v-bind()`、`:deep()`、`:slotted()`、`<style module>` を使うルールのグローバル化
- メディアクエリの条件のトークン化 (`@media` の条件に `var()` は使えない)

## 適用時の注意

- **トークン化は挙動不変**: 値を正規化 (4px→8px など) しない。既存値をそのまま変数に置き換える
- トークン名は既存の変数命名と整合させる (小文字ハイフン: `--text-xs`, `--space-sm` など)
- 色は通常テーマ CSS の変数 (`--primary` 等) が既にある — 色のハードコードを確認したら
  テーマ変数が既に定義されていないか先に確認する
- scoped 削除後の空 style ブロックは削除する
- 変更後は見た目を確認する。型チェック・テスト・ビルドでは検出できない (SKILL.md Step 4)
- コミットする場合は 1 問題 1 コミットとし、commit スキルの手順に従う
