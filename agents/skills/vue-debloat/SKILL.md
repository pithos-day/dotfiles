# Vue Debloat Skill

## 目的

Vue コンポーネントの `<script>` と `<style>` の肥大化を「理解にかかる時間の最小化」の観点で診断し、適切な抽出先へ分離する。
リファクタリングの原則 (挙動不変・小さな独立した変更) に従う。

## Step 1: 対象の把握

- 対象の `.vue` ファイルの行数を確認し、`<script>` と `<style>` の行数を分けて数える
- API スタイルを確認する。判定基準は Composition API (`<script setup>`) が前提。Options API なら、移行を含めずに適用できる範囲をユーザーに確認する
- プロジェクトの配置 (composable・lib・グローバル CSS の場所) を確認し、既存の配置に従う
- テストの有無とテストコマンドを確認する (テストがなければ構造変更の前にユーザーに確認)
- style を変更する場合は、見た目の確認手段を確認する (Step 4)
- `git status --short` とブランチを確認し、作業前から変更があるファイルを控える
- 依頼が「診断のみ」か「修正まで」か、修正ならコミットまで行うかを依頼文から判断し、不明な場合だけ確認する

## Step 2: 診断

`references/script-checklist.md` と `references/style-checklist.md` のチェックリストを走査し、
問題箇所を **ファイル:行番号 + 問題 + 該当原則** の形で列挙する。

- まず表面的な問題 (重複・ハードコード値) から走査し、構造的な変更 (分割・抽出) は後回しにする
- 問題には重要度を付ける: High (複数ファイル重複・著しい肥大) / Medium (単独だが利益あり) / Low (任意)
- 横断的な重複 (同一ルールセット・同一値が 3 コンポーネント以上) は優先的に報告する

## Step 3: 分離先の選定

### script 側

| 分離先 | 判定基準 |
| --- | --- |
| composable | 状態 (ref/reactive) + 処理が一まとまりで、複数コンポーネントで再利用される/されうる (例: ドラッグ定型・キーハンドラ・フォーム処理) |
| 素の .ts (lib/) | Vue に依存しない純ロジック (計算・変換・フォーマット・定数テーブル・型定義) |
| 子コンポーネント | script が 200 行超かつ責務が明確に複数で、template も責務ごとに区切れる (canvas 共有の描画は分割困難 — 描画関数の lib 化を優先) |

### style 側

| 分離先 | 判定基準 |
| --- | --- |
| グローバル CSS | 完全同一のルールセットが 3 コンポーネント以上 (例: `.grow` が 4 ファイル)。同名クラスの全使用箇所を確認してから移す |
| CSS 変数 (デザイントークン) | 頻出値のハードコード (font-size・gap・padding 等)。基準は `references/style-checklist.md` の S1。トークンは**値の正規化をせず**、既存値のまま変数化する (挙動不変) |
| 共通クラス | グローバル CSS に既に存在するクラス (.row, .btn 等) の scoped 再定義を削除。詳細度の変化を確認する |
| 子コンポーネント | style が 300 行超、または責務が混在 (ロジック分割と一貫させる) |
| 指摘のみ | 深いセレクタ・`!important` の多用。修正は詳細度が変わるため、依頼があり見た目を確認できる場合だけ行う |

## Step 4: 適用

1. 各変更は振る舞いを変えない (値・表示・挙動を保つ)
2. 型チェック・テスト・ビルドを実行する。検証コマンドはプロジェクトの AGENTS.md / package.json から特定する (例: `pnpm test` / `npx vue-tsc -b`)
3. style を変更したら、これらの検証では見た目の変化を検出できないため、変更前後のスクリーンショットを比較する (claude-in-chrome / Playwright など)。比較できない場合は「見た目は未検証」と報告し、確認箇所を挙げてユーザーに確認を依頼する
4. コミットを依頼されている場合は **1 修正 = 1 コミット** とし、commit スキルの手順に従う。検証が失敗したらコミットしない。デフォルトブランチにいる場合や、対象ファイルに作業前からの変更がある場合は、コミット前にユーザーに確認する

## Step 5: 報告

- 指摘は `ファイル:行番号` 形式で、修正提案は Before/After で示す
- 最終報告は「変更箇所 → 適用した原則 → 検証結果」の 3 点に絞る。見た目を確認していない style 変更は未検証と明記する
- 診断のみの依頼なら、件数サマリー (種別 × 重要度) を付けて、修正はユーザーの指示を待つ

## Gotchas

### script

- **過剰抽出に注意**: 1 コンポーネント専用の 15 行以下のロジックを composable 化しない (ローカル関数で十分)。composable に抽出してさらに子コンポーネント化する「二重抽出」も避ける
- **シングルトン化**: `ref` を composable 関数の外 (モジュールスコープ) に置くと全インスタンスで共有される。インスタンスごとの状態は関数内で作る
- **リアクティブ性の喪失**: `reactive` の戻り値を分割代入すると追従しなくなる。composable は `ref` を返すか `toRefs` を使う
- **ライフサイクルフック**: `onMounted` などは setup 中に同期的に呼ぶ。composable を `await` の後や非同期コールバックから呼ぶと登録に失敗する
- **props 配線コスト**: 深い v-model (例: `row.items[i].value`) を子コンポーネント化すると getter/setter の配線が増え、逆に読みにくくなる。分割より共通 lib/composable 化で縮小できるか先に検討する
- **canvas 共有**: 1 つの canvas に複数の描画領域がある場合、子コンポーネント分割は DOM 構造の変更を伴いリスクが高い。描画関数の lib 化を優先する
- 抽出した純関数 (lib/) には**テストを追加**する (テスト可能になったものはテスト対象にする)

### style

- **「完全同一」でも安全とは限らない**: scoped の `.row[data-v-x]` はグローバルの `.row` より詳細度が高い。scoped 定義を削除すると、別のルールに負けて見た目が変わることがある
- **グローバルへの漏れ**: scoped からグローバルへ移すと、同名クラスを持つ他のコンポーネントにも適用される。移す前に同名クラスの全使用箇所を確認する
- **移動できない記法**: `<style>` 内の `v-bind()`、`:deep()`、`:slotted()`、`<style module>` は SFC に依存する。グローバル CSS へそのまま移さない
- **`@media` と CSS 変数**: `@media (max-width: var(--x))` は機能しない。メディアクエリの条件はトークン化しない
- **トークン化は挙動不変で**: 値を正規化 (4px→8px など) しない。既存の値をそのまま `var(--xxx)` に置き換える

### 共通

- **既存規約が最優先**: プロジェクトの AGENTS.md・テストコマンド・コミット規約 (commit スキル) に従う
- **挙動が変わったと気づいたら停止**: 自分の変更だけをリバートし、ユーザーに報告してから方針を確認する。作業前から変更があるファイルには `git restore` などを使わず、自分の編集だけを手で戻す
