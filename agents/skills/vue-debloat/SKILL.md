# Vue Debloat Skill

## 目的

Vue コンポーネントの `<script>` と `<style>` の肥大化を「理解にかかる時間の最小化」の観点で診断し、適切な抽出先へ分離する。
リファクタリングの原則 (挙動不変・小さな独立した変更・1変更1コミット) に従う。

## Step 1: 対象の把握

- 対象の `.vue` ファイルの行数を確認し、`<script>` と `<style>` の行数を分けて数える
- テストの有無とテストコマンドを確認する (テストがなければ構造変更の前にユーザーに確認)
- 依頼が「診断のみ」か「修正まで」かを確認する

## Step 2: 診断

`references/script-checklist.md` と `references/style-checklist.md` のチェックリストを走査し、
問題箇所を **ファイル:行番号 + 問題 + 該当原則** の形で列挙する。

- まず表面的な問題 (名前・重複・ハードコード値) から走査し、構造的な変更 (分割・抽出) は後回しにする
- 問題には重要度を付ける: High (複数ファイル重複・著しい肥大) / Medium (単独だが利益あり) / Low (任意)
- 横断的な重複 (同一ルールセット・同一値が 3 コンポーネント以上) は優先的に報告する

## Step 3: 分離先の選定

### script 側

| 分離先 | 判定基準 |
| --- | --- |
| composable | 状態 (ref/reactive) + 処理が一まとまりで、複数コンポーネントで再利用される/されうる (例: ドラッグ定型・キーハンドラ・フォーム処理) |
| 素の .ts (lib/) | Vue に依存しない純ロジック (計算・変換・フォーマット・定数テーブル・型定義) |
| 子コンポーネント | script が 200 行超かつ責務が明確に複数 (canvas 共有の描画は分割困難 — 描画関数の lib 化を優先) |

### style 側

| 分離先 | 判定基準 |
| --- | --- |
| グローバル CSS | 完全同一のルールセットが 3 コンポーネント以上 (例: `.grow` が 4 ファイル) |
| CSS 変数 (デザイントークン) | 頻出値のハードコード (font-size・gap・padding 等)。トークンは**値の正規化をせず**、既存値のまま変数化する (挙動不変) |
| 共通クラス | global.css に既に存在するクラス (.row, .btn 等) の scoped 再定義を削除 |
| 子コンポーネント | style が 300 行超、または責務が混在 (ロジック分割と一貫させる) |

## Step 4: 適用

1. **1 修正 = 1 コミット**。複数の問題を 1 コミットにまとめない
2. 各変更は振る舞いを変えない (値・表示・挙動を保つ)
3. ステージは**対象ファイルを 1 つずつ明示指定**する (`git add <file>`)。`git add -u` / `git add -A` / `git add .` は禁止 (コミットし忘れた変更を巻き込むため)
4. コミット前に `git status --short` で untracked (`??`) と変更一覧を確認し、コミット後にクリーンであることを確認する
5. 型チェック・テスト・ビルドが通ってからコミットする (失敗したらコミットしない)。
   検証コマンドはプロジェクトの AGENTS.md / package.json から特定する (例: `pnpm test` / `npx vue-tsc -b`)

## Gotchas

- **過剰抽出に注意**: 1 コンポーネント専用の 15 行以下のロジックを composable 化しない (ローカル関数で十分)。composable に抽出してさらに子コンポーネント化する「二重抽出」も避ける
- **props 配線コスト**: 深い v-model (例: `row.unit[osc].freq`) を子コンポーネント化すると getter/setter の配線が増え、逆に読みにくくなる。分割より共通 lib/composable 化で縮小できるか先に検討する
- **canvas 共有**: 1 つの canvas に複数の描画領域 (鍵盤・グリッド・ノート) がある場合、子コンポーネント分割は DOM 構造の変更を伴いリスクが高い。描画関数の lib 化を優先する
- **トークン化は挙動不変で**: 値を正規化 (4px→8px など) しない。既存の値をそのまま `var(--xxx)` に置き換える。1 回きりの値 (1-2 箇所) はトークン化しない
- **scoped 再定義**: global.css に既存のクラス (.row, .btn, .grow 等) がコンポーネント内に scoped で再定義されていないか確認する。完全同一なら削除
- **既存規約が最優先**: プロジェクトの AGENTS.md・テストコマンド・コミット規約 (commit スキル) に従う
- **挙動が変わったと気づいたら停止**: 変更をリバートし、ユーザーに報告してから方針を確認する
- 抽出した純関数 (lib/) には**テストを追加**する (テスト可能になったものはテスト対象にする)

## Step 5: 報告

- 指摘は `ファイル:行番号` 形式で、修正提案は Before/After で示す
- 最終報告は「変更箇所 → 適用した原則 → 検証結果」の 3 点に絞る
- 診断のみの依頼なら、件数サマリー (種別 × 重要度) を付けて、修正はユーザーの指示を待つ
