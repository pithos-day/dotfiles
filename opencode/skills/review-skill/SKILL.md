# Skillレビュー

## 目的

特定のSkillが、実務で再利用され、チームの生産性を上げる設計になっているかをレビューする。
単なるMarkdown添削ではなく、Skillの起動性、専門性、段階的開示、運用性、改善余地を評価する。

## 入力

- レビュー対象の `SKILL.md` またはSkillディレクトリ
- 任意: 想定利用者、利用例、失敗例、チーム配布先、導入予定タイミング
- 任意: descriptionのみ、構成のみ、運用設計のみなどの重点観点

## レビュー手順

1. 対象を特定する
   - ディレクトリ指定なら `SKILL.md` と `references/`、`scripts/`、`assets/` を確認する。
   - descriptionだけが提示された場合は、本文・資材が未確認であることを明示してレビューする。
2. ローカルファイルをレビューする場合は、補助スクリプトで構造を棚卸しする。
   - 例: `python3 <このスキルのベースディレクトリ>/scripts/inspect_skill.py <レビュー対象のスキルディレクトリ> --format markdown`
   - ベースディレクトリは、スキル起動時に提示されるこのスキル自身のディレクトリ（配布先の例: `~/.claude/skills/review-skills`）を使う。リポジトリルート相対のパスを前提にしない。
   - スクリプト結果は機械的な検査として扱い、最終判断はSkillの目的と利用文脈に合わせて行う。
3. Skillを1つの主カテゴリへ分類する。
   - 9カテゴリと評価基準は `references/review-rubric.md` を読む。
   - 複数カテゴリにまたがる場合は、分割またはdescriptionでのスコープ制御を提案する。
4. 有効性を評価する。
   - `references/review-rubric.md` の10観点を0〜2点で採点し、総合判定とブロッカー有無を決める。
5. 改善案を作る。
   - 重要度順に、根拠、影響、具体的な修正方針を書く。
   - 必要なら改訂description、見出し構成、リソース分割案、Gotchas候補、計測・展開プランを提示する。
   - ユーザーが明示的に依頼していない限り、レビュー対象ファイルを直接編集しない。

## 評価のコツ

- 「scriptsやhooksが無いから低評価」とは判断しない。反復性・脆弱性・安全性に応じて必要性を評価する。
- 「長いSkill」は悪ではないが、常時読むべきでない詳細が本文にある場合は `references/` へ分離する。
- 「便利そう」ではなく、起動条件、再現可能な成果物、失敗時の挙動、チーム展開まで確認する。
- 一般論の繰り返しや過度な手順固定（railroading）があれば、実際の失敗例ベースのGotchasへの置き換えを提案する。
- 破壊的操作、外部送信、チケット作成、push、デプロイを伴うSkillでは、事前確認・dry-run・権限境界を重点確認する。
- このスキル自身の誤評価（過剰指摘、見落とし、スクリプト結果の鵜呑み）に気づいたら、その実例をこの「評価のコツ」へ追記して育てる。

## 出力形式

標準形式は `references/output-template.md` を使う。
短いレビューを求められた場合も、最低限「総合判定」「重要指摘」「改訂description案」「次アクション」を含める。
