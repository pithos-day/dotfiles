# 構造チェックリスト

## 1. 無関係なサブ問題を抽出する

> **「攻撃的に」無関係なサブ問題を見つけて抽出する。**

進め方:
1. コードの高レベルの目標を問う
2. 各行に「この目標に直接働いているか? それとも別のサブ問題を解いているか?」と問う
3. 十分な行がサブ問題を解いているなら、別関数に抽出する

- 例: `findClosestLocation()` 内の球面距離計算 → `spherical_distance()` として抽出。読者は高レベルの目標に集中でき、`spherical_distance()` は単体テスト可能・再利用可能。
- **純粋なユーティリティ**: 「ライブラリに `XYZ()` があればいいのに」と思ったら自分で書く(`ReadFileToString()`)。`util/` ディレクトリに蓄積していく。
- **分離には予想外の利点**: `format_pretty(obj)` を分離すると、その関数だけを改善(エッジケース処理、再帰)するのが容易になる。
- **プロジェクト固有でも効果は同じ**: ビジネス名→URL 変換(`make_url_friendly()`)を抽出。
- **インターフェースを自分の都合に合わせる**: 使いにくい API はラッパーで隠す(`get_cookie()` / `set_cookie(name, value, days_to_expire)` / `delete_cookie(name)`)。「不完全なインターフェースに甘んじる必要はない」。
- **やり過ぎ注意**: 細かすぎる関数分割は読む量を増やし、実行パスを追うのにジャンプが必要になる。**関数を1つ追加するには読みやすさのコストがかかる**。利益が釣り合うときだけ(他の場所からも必要になる等)。

> 要点: 汎用コードとプロジェクト固有コードを分離する。残るのは「あなたのプログラムをユニークにする小さなコア」だけ。

## 2. 一度に1つのタスク

> **コードは一度に1つのタスクだけを行うように組織化する。**

進め方:
1. コードが行っている「タスク」をすべて列挙する(小さくてよい。「オブジェクトが有効か確認する」でも「ツリーの全ノードを走査する」でも)
2. タスクを別関数、または少なくとも別のコードセクションに分離する

- 例: `vote_changed()` の「投票を数値へ変換」と「スコア更新」を分離 → `vote_value(vote)` ヘルパーで `score += vote_value(new_vote)` に単純化。
- 例: `location_info` から「都市/国を選ぶ」コード → 抽出(1) → デフォルト値の整形(2) → 結合(3) の領域に分割。`a || b || c`(最初の truthy)を使えばさらに簡潔に。
- 例: `UpdateCounts()` — 「デフォルト値の定義」「値を抽出」「counts[] を更新」の3領域に分割。**関数分割は必須ではない** — 同じ関数内の段落分けでも効果はある。列挙したタスクの一部だけ分離できても十分。
- 「関数は1つのことだけをするべき」という古いアドバイスより実践的: 関数境界を越えずとも、コード内に論理的なセクションを作る。

## 3. 考えを言葉にしてからコードにする

> **コードが何をすべきかを平易な言葉で説明し、その説明にコードを合わせる。**

進め方:
1. コードの動作を、同僚に話すように平易な言葉で説明する
2. 説明で使った重要な単語・フレーズに注目する(そのまま名前・構造になる)
3. 説明に合わせてコードを書く

- 例: 権限チェックを「管理者であるか、文書の所有者であるか」と説明 → 否定のない `if (is_admin_request()) ... elseif ($document && ...)` の形に。
- 例: tips 表示を「現在の tip を隠して、次の tip を表示する」と説明 → jQuery の `.next()` を使って整数操作なしのコードに(ライブラリ知識が役立つ)。
- 大きな問題にも再帰的に適用: 3つのイテレータを揃える複雑なロジック → `AdvanceToMatchingTime()` を説明文から導出し、変数名も `t1, t2, t3` に一般化。
- **「ラバーダッキング」**: 説明できないコード・設計は、何かが欠けているか未定義。言葉にできないものは形にできない。

## 4. 書くコードを減らす

> **最も読みやすいコードは、コードがないこと。**

- **実装するべきでない機能を実装しない**: 不要機能・未完成機能はプロジェクトを重くする。実装コストはプロトタイプだけでなく「保守・ドキュメント・コードベースの重量」まで含む。
- **要件を疑い、分解する**: 必ずしも高速・完全正解・全入力対応は要らない。
  - 例: 店舗検索 — 「テキサス州の30店舗」なら国際日付変更線・極地・地球の曲率の処理を要求から外し、ユークリッド距離で十分。
  - 例: キャッシュ — 連続アクセスが多いなら LRU キャッシュ(100行)の代わりに**1アイテムキャッシュ**(数行)で90%の利益。
- **コードベースを小さく保つ**: 汎用ユーティリティで重複を除去、**未使用コードを削除する**(「書いた労力を無駄にしたくない」を克服する。庭師が剪定するように)。直交しない機能を条件付きで埋め込まない。
- **ライブラリに精通する**: 定期的に15分だけ標準ライブラリの関数名を読む。例: 重複除去を自前の辞書で実装せず `set` を。
- **コードを書かない選択肢**: Unix ツールのパイプライン等、プログラムを書かずに済ませる方法もある。

## 診断時のチェック項目 (要約)

- [ ] 高レベルの目標から「無関係なサブ問題」が抽出されていないか
- [ ] 使いにくい API のグルーコードが散らばっていないか (ラッパーを作れる)
- [ ] 1つの関数・ブロックが複数のタスクを織り交ぜていないか
- [ ] デフォルト値の定義・値の抽出・集計・出力などが混在していないか
- [ ] コードの意図を言葉で説明できるか (できないなら設計欠陥の疑い)
- [ ] 不要な機能・未使用コード・完成していない変換コード等が残っていないか
- [ ] 手書きで実装している処理が標準ライブラリ・既存ユーティリティで置き換えられるか
- [ ] 関数分割が細かすぎる・深すぎる場合分けになっていないか (やり過ぎチェック)
